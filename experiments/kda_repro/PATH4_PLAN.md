# Path4：KDA 复现与国产 GPU 迁移简要计划

日期：2026-09-19。当前仅整理计划，暂停新增 GPU 测试和模型 API 调用。

## 1. 目标与当前基础

**先在现有 V100 上完成可追溯的 Agent 自动优化闭环，再在天数 BI-V150 上验证一个算子的迁移。**
近期交付是：模型提出修改、生成候选、自动验证、测量性能、根据证据保留或淘汰，并完整保存过程。

现有基础：GDN Decode 的 54 组、GDN Prefill 的 100 组官方输入已完成 V100 适配验证，见
[Decode 报告](OFFICIAL_V100_RESULT.md)和[Prefill 报告](PREFILL_V100_RESULT.md)。
这些结果属于已有实现及调度验证；学校 API 已连通，但首轮代码生成返回空内容，尚未证明 Agent 能独立完成有效优化。

KDA 官方提供通用工作流；竞赛发布还采用 Humanize、KernelWiki 和 ncu 分析工具。
现有自编 API 控制器应标为“参照 KDA 的工作流适配”，其与官方工具链的差异需要记录。
依据：[KDA 工作流](https://github.com/NVlabs/kda/blob/main/docs/agent-flow.md)、
[竞赛发布说明](https://github.com/mit-han-lab/mlsys2026-flashinfer-contest)。

## 2. 三个算子仓库怎么用

| 仓库 | 本项目用途 | 优先级 |
|---|---|---|
| [FlagGems](https://github.com/flagos-ai/FlagGems/blob/master/README_cn.md) | 优先选取 Triton 算子、测试与性能基线；已有 [Iluvatar 后端](https://github.com/flagos-ai/FlagGems/tree/master/src/flag_gems/runtime/backend/_iluvatar)，与现有代码路线接近 | 第一 |
| [InfiniCore](https://github.com/InfiniTensor/InfiniCore) / [InfiniOps](https://github.com/InfiniTensor/InfiniOps) | 参考厂商后端实现与跨平台接口，必要时提供第二组基线；当前 InfiniCore 已分为运行时、算子和通信组件，不能简单概括成纯 CUDA 算子库 | 第二 |
| [DIOPI](https://github.com/DeepLink-org/DIOPI) | 借鉴算子输入输出约定、边界用例和正确性测试，暂不作为主要开发底座 | 辅助 |

本次可读取的 DIOPI 主分支[提交记录](https://github.com/DeepLink-org/DIOPI/commits/main)顶部日期为 2024-11-22，可说明更新较久；不据此推断所有分支、后端都已停止维护。
仓库支持天数后端，并不代表每个算子都能直接在本机软件版本运行；实施时固定提交并核对具体覆盖情况。

## 3. 实施顺序与预估

以下为一名主要实施人员、现有环境可用时的工程估计，不含排队、权限审批和长时间依赖排障。

| 阶段 | 怎么做 | 交付与验收 | 预计工作日 |
|---|---|---|---:|
| A：补齐闭环 | 处理 API 空返回、截断与超时；固定模型、输入、容差和预算；限制候选修改范围 | 至少一个模型生成候选完成编译、全量正确性验证与计时；失败原因可追溯 | 1 |
| B：验证优化价值 | 先做已有数据与验证器的 GDN Decode，再扩展 Prefill；从同一起点比较固定参数搜索和 Agent 修改 | 记录正确率、有效候选数、最佳延迟、调用成本；确认收益是否来自 Agent | 2–3 |
| C：迁移到天数 | 优先 Residual Add RMSNorm；借鉴 FlagGems，核对后端与语义，使用天数适配软件栈重新优化；后续再考虑 SwiGLU | 一个算子在 BI-V150 上完成正确性与性能闭环；纳入训练时补齐前向、反向验证 | 2–3 |
| D：整理成果 | 汇总固定版本、一键脚本、候选代码和原始数据 | 一份可提交报告，区分已有实现、Agent 新改进和迁移结果 | 1 |

**首阶段 A+B+D 约 4–5 个工作日；包含天数迁移约 6–8 个工作日。**
如果基线已经较好，完整记录“无稳定改进”也是有效结果，不通过放宽误差或换弱基线制造加速。

## 4. 卡与调用预算

- **现在继续使用一张 V100 32GB。** 已有环境和数据可复用，模型通过学校 API 调用，无需在这张卡部署大模型。建议配 8–16 核 CPU、32–64GB 主机内存。
- **国产适配阶段使用一张 BI-V150 32GB。** 先用已验证的软件组合；按其编译器和运行时重新生成候选，不直接照搬 NVIDIA 专用实现。
- **对齐官方竞赛成绩时再申请 B200。** 官方复现指定 B200 兼容路径及锁定依赖，V100 或天数上的适配结果不能等同于官方验收。[官方复现说明](https://github.com/mit-han-lab/mlsys2026-flashinfer-contest/blob/main/docs/reproduction.md)
- 首阶段暂预留 **10–30 GPU 小时**，天数试点另预留 **5–15 GPU 小时**，均为排期预算而非实测耗时；首轮完成后按编译、验证和等待 API 的实际时间修正。
- API 先做至多 **10 轮候选生成**的小试，设置重试和输出长度上限。记录输入/输出 token 与学校计费口径，再确定扩大预算；当前单价未知，不估算人民币费用。

## 5. 如何判断做成了

1. **闭环成功：** 保存模型建议、完整代码、错误反馈、验证和计时，能说明每个候选为何保留或淘汰；API 连通本身不算成功。
2. **性能可信：** 同卡、同输入、同精度比较；候选与基线交替重复计时，最终候选独立复测。保留逐形状结果和整体几何平均，列出退化形状。
3. **Agent 贡献可辨：** 在相同起点及评估次数预算下，对比固定参数搜索与 Agent；小试后至少进行三次独立搜索，报告波动。把“稳定提升约 5%”作为探索目标，不作为保证。
4. **基线有竞争力：** PyTorch 用于语义校验，同时尽可能对比同语义的 FlagGems/厂商优化实现；只快于未融合 PyTorch 时，明确说明比较范围。
5. **结果可复现：** 固定源码、数据、环境、模型标识和提示词，保存原始报告及一键命令。现有 ncu 权限受限，先记录计时和显存，待平台授权后补充硬件分析。

本轮聚焦 Path4。它可为原项目“自动化算子优化”提供基础，但不等于完成五个训练算子、四个微调算子，也不构成 Poly 模块或 Halide IR 规范化成果；这些指标后续另行对接。
