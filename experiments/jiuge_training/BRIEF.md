# 九格7B训练与微调 tracing 简报

截至2026年10月23日；已验收的正式性能数据截至10月20日。

**官方九格7B在ACT双A100上完成训练与全参数微调的原生tracing，并新增16份SFT原生/修复版对照时间线。优化对象是CPU AdamW offload中的FP32主参数pinned memory问题：SFT正式吞吐相对原生Megatron提升92.9%，此前CPT的独立正式提升为84.4%。新时间线显示，主要变化是HtoD主机调用耗时缩短，CPU AdamW可与HtoD搬运重叠；模型计算和AdamW更新公式保持不变。**

## 1. 实验配置与采集结果

模型为官方九格 `9G7B_MHA`，28层、约76.69亿参数。采用Megatron、双A100 40GB、TP2、BF16、序列长度2048、micro/global batch均为1，使用原生AdamW CPU offload。数据为48,818条中文Alpaca指令数据。

| 任务 | 训练方式 | 完成情况 |
|---|---|---|
| 继续预训练 CPT | 指令、输入和答案全文参与next-token loss | 3步准入检查＋35步真实参数更新，4份trace |
| 全参数微调 SFT | 仅答案和结束标记参与loss，提示部分被mask | 3步准入检查＋35步真实参数更新，4份trace |
| SFT原生/修复配对 | 同一官方模型和SFT数据，原生—修复—修复—原生 | 每次35步，共16份双rank窗口trace；样本编号、监督目标计数及35条日志loss一致 |
| SFT NUMA对照 | 在已验收pinned版本上比较不绑核、GPU本地绑核、两插槽分散绑核 | 六次独立初始化、每次35步，共24份trace；样本、监督计数和日志loss一致 |

每次采集第21–25、31–35步，两个rank各保留两个窗口。时间线包含完整训练步中的前向、反向、优化器更新、GPU计算、搬运和NCCL通信；覆盖GEMM、MHA attention、RMSNorm、SwiGLU、RoPE、交叉熵及CPU AdamW。SFT实际输入和答案mask已独立核验，所有参数参与更新。

**采集范围为稳定阶段的完整训练步窗口，未连续录制从启动到结束的全部35步。** 本轮使用原生Torch后端，未加入新的Triton算子。原件、日志及压缩/解压SHA保存在ACT，本机只保存精简关键结果。

## 2. 时间线分析与主要瓶颈

10月17日原生CPT/SFT时间线显示CPU优化器/offload范围占窗口约56%–68%，GPU纯计算约0.7秒/步，因此优先排查offload路径。10月20日晚在**同一对A100**重新采集原生和修复版SFT，采用ABBA顺序，避免直接比较不同卡对上的时间线。

以下为各组8个rank/window观测的均值，时间按五步窗口均摊为每rank每步；它们不是8个独立种子。

| 观察量 | 原生SFT | pinned修复版 |
|---|---:|---:|
| CPU优化器外层范围 | 5.74秒 | 2.55秒 |
| CPU AdamW更新函数范围，不含搬运post-hook | 2.63秒 | 2.32秒 |
| HtoD的CPU API范围 | **2.90秒** | **4.33毫秒** |
| CPU AdamW与HtoD重叠 | **0秒** | **1.58秒** |
| HtoD数据量 | 14.29GiB | 14.29GiB |
| GPU纯计算区间并集 | 0.678秒 | 0.661秒 |
| NCCL区间并集 | 1.01秒 | 0.48秒 |
| NCCL区间中与GPU计算重叠的比例 | 8.4% | 12.8% |
| 未记录GPU活动的空档比例 | 28.8% | 10.0% |

**改善的是offload路径：数据量相同，但大块HtoD从普通主机内存转为pinned路径，主机调用耗时显著缩短，并能与CPU AdamW更新重叠。** GPU计算耗时接近；本轮没有新增Triton kernel。

DtoH的单向GPU区间由1.35秒增至1.71秒，但它与AdamW的重叠由0.62秒增至1.60秒；总GPU memcpy区间仍由3.60秒降至2.18秒。这也说明应以端到端结果和时间线判断收益，不能将各项耗时相加。

![SFT原生与pinned修复的配对时间线分析](results/sft-paired-trace-comparison-20261020.png)

修复后的主要观察：

- **CPU AdamW仍需关注。** 更新函数范围约2.32秒/步，后续应区分CPU内存带宽、NUMA放置和逐参数调用开销。本轮未对这些因素做因果隔离。
- **通信重叠仍有限。** 每个五步窗口、每rank仍有922个NCCL kernel；仅约12.8%的NCCL区间与GPU计算重叠，窗口内未观察到NCCL与GPU memcpy重叠。NCCL时长可能包含rank等待，不能等同于链路传输时间。
- **rank到达偏差有所收敛的候选证据。** 按可匹配通信签名统计，每窗口最大启动偏差候选范围由1.55–2.33秒降为0.16–0.64秒；原生通信序号及完整因果关键路径尚未建立。

CPU范围、GPU计算、搬运和通信可以重叠，表格各行不能相加。CPU API范围不是独立测得的暴露等待；GPU空档也不是硬件利用率。本轮profiling解释机制，正式吞吐提升仍以独立无profiler验收为准。

## 3. 吞吐提升结果与基线定义

### 3.1 继续预训练 CPT（10月16日）

**比较对象：同一九格7B继续预训练任务、相同双A100和训练配置下，“pinned memory修复版”相对“原生Megatron CPU offload后端”的端到端训练吞吐。**

原生后端按相同offload/pin参数运行，但最终CPU FP32主参数未保持pinned属性。修复在CPU复制和FP32转换之后确保最终主参数使用pinned memory，改善后续搬运路径；模型结构、训练数据、精度和AdamW更新数学保持一致。

| 后端 | 三种子平均step耗时 | 合并有效吞吐 |
|---|---:|---:|
| 原生Megatron（主基线） | 6.581秒 | 311.2 tokens/s |
| control：原生方法的独立副本 | 6.623秒 | 309.2 tokens/s |
| pinned memory修复版 | **3.592秒** | **570.2 tokens/s** |

84.4%按三个种子各自的吞吐比取几何平均：

```text
r = 同一种子的修复版吞吐 / 原生吞吐
提升 = [(r1 × r2 × r3)^(1/3) − 1] × 100% = 84.4%
```

三种子配对几何平均吞吐比为：相对原生 **1.844倍（+84.4%）**，相对control **1.856倍（+85.6%）**。表中吞吐是总有效token除以总保留耗时，属于合并统计，与逐种子配对几何平均的口径不同。

正式测试使用3个种子、native/control/optimized三组轮换，共9次独立运行；每次120步，排除前20步预热，关闭profiler和额外审计。沿用Megatron的GPU同步 `time.time` 计时，每个对齐区间取两TP rank较慢端，token数不因TP2翻倍。三个种子均更快；三步全状态及断点恢复/下一步对照通过，受检数值最大误差为0。修复版种子均值CV为13.6%，波动仍需后续复验。

**84.4%来自10月16日CPT的独立正式测试。10月17日的CPT/SFT tracing用于分析负载，不用于计算加速比。**

### 3.2 全参数微调 SFT（10月20日）

比较同一SFT任务中的原生Megatron、control独立原生副本和同一pinned修复。所有组使用同一物理双A100卡对及相同资源、模型、数据和精度配置，重新计时。

| 后端 | 三种子平均step耗时 | 合并输入token位置/s | 合并答案监督目标/s |
|---|---:|---:|---:|
| 原生Megatron | 6.563秒 | 312.0 | 263.3 |
| control独立原生副本 | 6.475秒 | 316.3 | 266.9 |
| pinned memory修复版 | **3.413秒** | **600.1** | **506.4** |

按三个种子的配对吞吐比取几何平均，修复版相对原生 **+92.9%（1.929倍）**，相对control **+90.3%**，三个种子均更快。表中为合并吞吐，统计口径与配对几何平均不同。每步计2048个输入位置；答案监督目标来自实际mask，TP2不使token数翻倍。

正式测试仍为9次独立运行、每次120步、剔除20步，使用相同的GPU同步计时及两rank对齐慢端。原生/control的种子均值CV为1.66%/0.41%，均未触发10%的完整复测条件；修复版CV为9.24%。三步全状态及原生检查点恢复/下一步比较的最大误差为0，覆盖每rank全部199组参数；正式120批样本及监督mask一致，13条日志loss也一致。ACT原件和最终726份关键文件均完成校验，双卡作业已结束，累计0.00点。

## 4. 适用范围与后续方向

当前结果适用于ACT单机双A100、TP2及上述CPU offload配置。天数BI-V150、8B/4B和多机通信仍需独立验证；当前trace尚不能证明零丢事件或完整因果关键路径。

修复后SFT的配对tracing和独立复核已完成，双卡采集作业自动结束，累计0.00点。后续重点是CPU AdamW/NUMA和通信等待的受控对照，继续沿用现有全状态正确性、原生断点恢复及三种子正式性能标准。原始trace、张量、检查点和日志留在ACT，本机只保留关键结果及图表。

10月21日的六组NUMA对照已完成，新增24份时间线。以下是开启profiler后的窗口耗时，仅作诊断：

| 方案 | 两次运行的慢rank窗口均摊耗时 | CPU AdamW范围均值 |
|---|---:|---:|
| 不绑核，pinned基线 | 2.873 / 3.500秒/步 | 1.953秒/步 |
| GPU本地8核/rank | 3.801 / 3.907秒/步 | 2.606秒/步 |
| 两CPU插槽各8核 | 2.878 / 2.881秒/步 | 1.679秒/步 |

**GPU本地绑核两次都更慢；分散方案较稳定，但未稳定优于不绑核。** 页采样发现，即使CPU已绑到GPU所在节点，AdamW的moment状态仍可能主要位于另一节点。因此，后续应先控制实际状态页位置，再判断绑核是否有效。三组GPU计算均约0.66秒/步，NCCL与计算的重叠仍约13.5%–14.1%，采样窗口内未观察到NCCL与memcpy重叠。

本轮两项NUMA候选均未通过筛选，**没有新增正式加速比**，暂不直接进入大规模验收。既有SFT +92.9%和CPT +84.4%结论不变。双卡作业已完成、退出码0、累计0.00点，24份原始时间线及完整日志留在ACT，压缩和解压SHA均已核验；本机仅保留关键结果。

新候选将AdamW的两个moment状态放到执行CPU所在节点，保留既有pinned修复和更新公式。CPU小样本及原生CPU恢复检查均逐位一致，但7B双卡实验在候选第1次更新时发生OOM，作业已结束、累计0.00点。此前两组对照各完成35步，共8份时间线；完整六组筛选未完成，**没有新增性能结论**。73份冻结来源及失败日志保留，下一项先排查并降低状态创建与复制时的内存峰值，再考虑重新筛选。[诊断与失败记录](README.md#二十adamw状态页就近放置候选10月21日候选首步oom)

这8份时间线和失败原件共73.3MB，仅保存在ACT，压缩及解压SHA已核验；本机关键包不足1MB。[失败材料与两组完成状态复核](results/sft-moment-screen-failure-independent-key-review-20261021.json)
