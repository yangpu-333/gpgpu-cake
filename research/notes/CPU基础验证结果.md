# 本机 CPU 基础验证结果

执行时间：2026-09-09 22:35（北京时间）。环境：Windows 11、Python 3.12.14；仅使用 Python 标准库。

**目前获得的成果是：一套已经实际运行、能重复检查分块计算和拦截部分常见错误的 CPU 验证程序。** 它可以作为后续接入编译器和 GPU 前的流程基础；本次没有测算子性能，也没有执行 Halide、Poly 或 Triton GPU 代码。

## 覆盖了哪些情况

- 向量长度：1、3、4、5、15、16、17、31、32、33、129、1024；分块大小：1、4、16、32、2048。
- 矩阵乘法尺寸按 `(M, N, K)` 记录：`(1,1,1)`、`(1,17,3)`、`(9,1,7)`、`(5,7,3)`、`(16,16,16)`、`(17,19,23)`、`(31,33,17)`、`(64,48,32)`；分块大小：1、2、4、8、128。即左矩阵为 M×K，右矩阵为 K×N。
- 数据：全零、−8 到 8 的小整数、−1 到 1 的随机浮点数；种子：0、7、41。

这些组合包含普通整块、不能整除的尾部、单行/单列、非方形矩阵，以及分块比整个输入还大的情况。它们更容易暴露“最后几个元素没有算到”等问题。

矩乘的小整数参考使用 Python 整数精确求和，并且本次乘积和累加值处于浮点数能够精确表示的范围；要求误差为 0。随机浮点参考使用 `math.fsum` 对浮点乘积作更精确的累加，固定 `atol = rtol = 1e-12`。`fsum` 不是精确实数矩乘：每个乘积本身仍可能舍入。相比只和同样顺序的浮点循环比较，这种参考增加了一层检查。

## 最值得保留的三个结论

**1. 分块和尾部处理在已测范围内可用，可以作为后续测试样例。**

通俗地说：把计算拆成不同大小的小份，最后剩下一点也能正确处理。这是目前的 Python 实现结果；将来编译器生成新代码时，可以复用这些输入与检查标准，再逐个验证新实现。

**2. “先判断算得对不对，再考虑速度”的筛选规则已经有可执行检查。**

本次故意加入尾部错值、缺少元素、NaN（非数值）和无穷大，都被拒绝。再给这些错误候选设置一个虚构的很小耗时，选优函数仍只选正确候选；没有正确且有有效耗时的候选时，返回“没有可选项”。这些虚构耗时只用于检查规则，没有实际测量 CPU/GPU 速度，也没有验证 GPU 的启动和计时路径。

**3. 浮点累加顺序需要成为后续优化的明确约束。**

本机用当前矩乘实现构造了一次三项累加：

```text
依次累加 10^16、1、−10^16 → 0
依次累加 10^16、−10^16、1 → 1
数学上的准确结果           → 1
```

原因是浮点表示的精度有限，较大的数和很小的数相加时，小量可能被舍掉。这为项目提供了一个具体的反例：**Halide IR 规范化和 Poly 变换应明确哪些浮点累加顺序必须保留，哪些变换需要额外误差验证。** 当前分块实现对同一输出仍按 K 递增累加，本例主动改变了项的顺序，不能解释为“改变分块大小导致了误差”。

## 暂时不能得到的结论

本次不能回答“哪种分块更快”“能提升多少性能”“天数 GPU 是否兼容”，也不能据此认定 Halide IR 规范化、Poly 模块优化或自动性能搜索已经完成。CPU 用的是 Python 数值和列表，不能替代 GPU 的 FP16/FP32、并行同步或训练梯度验证。

扩展检查整体约用 1.33 秒，这包含数据准备、参考计算和检查程序的开销，仅用于说明本机运行成本，不是算子耗时或加速比。
