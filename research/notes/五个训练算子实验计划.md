# Megatron-LM 五个训练算子实验计划

日期：2026-09-15  
目标框架：Megatron-LM `5be9626709af2722333bf54797c954c09edeada3`  
目标设备：Iluvatar BI-V150

## 1. 实验目标

围绕以下五个暂定训练算子建立可重复的自动优化实验：

1. Dense Fused Attention
2. Vocab-parallel Cross Entropy
3. SwiGLU
4. Residual Add RMSNorm
5. MoE Grouped GEMM

实验需要体现三个项目关键词：**Halide IR 规范化、Poly 模块优化、自动化算子优化流程**。第一阶段先证明基线、正确性检查和计时流程可信，再逐步接入 IR 与 Poly，不把手写参数枚举表述成已完成 Poly 优化。

四个微调算子尚未确定。本阶段在算子注册表和结果格式中预留 `fine_tuning` 类型，但不猜测具体算子。

## 2. 总体实验结构

使用两套小型 Megatron 配置，不依赖长时间完整训练：

- **Dense GPT 配置**：覆盖 Dense Fused Attention、Vocab-parallel Cross Entropy、SwiGLU、Residual Add RMSNorm。
- **MoE GPT 配置**：重点覆盖 MoE Grouped GEMM，并验证它接回真实 MoE 层后的影响。

每个算子做两层实验：

- **算子级微基准**：隔离前向、反向、显存和编译开销，便于搜索参数与定位问题。
- **Megatron 集成实验**：以短训练步骤验证梯度、模型损失、每步时间和吞吐量，判断算子提速能否转化为训练收益。

先从实际 Megatron 运行中采集形状、数据类型、布局和调用频次，再确定正式形状集。形状集分为搜索集和留出集，避免只对参与搜索的尺寸有效。

## 3. 分阶段执行

### 阶段 A：固定环境和基线

1. 检查 Megatron-LM 提交号必须与指定 commit 完全一致。
2. 记录 BI-V150 型号、卡数、驱动、PyTorch、Triton、Megatron 参数和源码哈希。
3. 跑现有 `basic_validation`，确认厂商 PyTorch/Triton 可以编译、执行和计时。
4. 用短训练采集五个算子的真实形状、dtype、stride、前向/反向耗时和峰值显存。
5. 保存 Megatron 当前可运行实现作为基线，不重新安装 CUDA、cuDNN 或覆盖厂商环境。

阶段产物是环境报告、原始形状清单和基线 JSON。基线必须能重复运行，之后才开始候选优化。

### 阶段 B：建立五个算子的正确性基准

为每个算子定义统一契约：输入、输出、可修改对象、精度、随机性、保存的反向状态和分布式通信语义。候选必须依次通过：

1. 前向输出对照；
2. 输入梯度和参数梯度对照；
3. 普通形状、边界形状及非整除形状；
4. 有限值、输入未被意外修改和越界写入检查；
5. 分布式算子的跨 rank 结果检查。

误差阈值在搜索前固定并写入算子配置，不能为某个候选临时放宽。正确性失败的候选不进入计时和选优。

### 阶段 C：先验证两个较简单的融合算子

优先实现 **SwiGLU** 和 **Residual Add RMSNorm**。它们便于确认 BI-V150 上的编译、融合、归约、向量化和反向流程。

- SwiGLU：搜索元素分块、向量宽度、warp 数和是否融合门控乘法。
- Residual Add RMSNorm：搜索行分块、归约方式、向量宽度、warp 数，并保证残差输出和归一化输出语义完整。

这一步形成首个“生成候选—检查—计时—选择—回退”的端到端闭环。

### 阶段 D：扩展到其余三个算子

| 算子 | 首轮重点 | 设备要求 |
|---|---|---|
| Dense Fused Attention | causal mask、缩放 softmax、Q/K/V 布局、前反向分块和融合边界 | 单卡先做；正式覆盖真实序列长度 |
| Vocab-parallel Cross Entropy | 稳定 softmax、target shard mask、前反向融合、通信与计算边界 | TP=1 检查本地数学；TP=2 才能验证 vocab parallel 语义 |
| MoE Grouped GEMM | experts 数、tokens/expert 不均衡、M/N/K 分块、空 expert 和尾部 | 单卡测本地 grouped GEMM；双卡补 expert parallel 路径 |

Attention 的实现复杂度最高，放在基础闭环稳定后。Cross Entropy 和 MoE 的单卡微基准只验证局部计算，不能替代双卡通信实验。

### 阶段 E：接入三个项目关键词

完整自动流程为：

```text
Megatron 真实调用
  → 提取算子契约与形状
  → Halide IR 规范化
  → Poly 依赖分析与调度候选生成
  → 静态合法性/资源检查
  → BI-V150 编译
  → 前向与反向正确性验证
  → 性能和显存测量
  → 选择正确且稳定的候选
  → Megatron 显式分派，不适用时回退基线
```

- **Halide IR 规范化**：统一等价的循环、索引、常量和缓冲区表达，保留归约顺序、数据类型、布局、边界和读写语义；规范化结果生成稳定哈希，作为工作负载身份与缓存键。
- **Poly 模块优化**：在可分析的仿射循环区域内检查依赖并产生 tiling、循环重排、融合、向量化等候选；softmax、随机 dropout 和通信等难以直接覆盖的部分保留显式边界及基线路径。
- **自动化算子优化流程**：自动生成候选、提前拒绝非法方案、先验正确性、再测速度、保存诊断并选择实现。LLM agent 后续可以提出调度候选，但实测系统和编译器共同决定候选是否有效。

## 4. 计时和选优规则

- 预热和编译不计入稳定 kernel 时间，但单独记录编译与总搜索成本。
- 使用设备事件测前向、反向和前反向合计时间，报告中位数、最小值、最大值及波动。
- 同轮候选交替执行，避免固定顺序偏差；正式结果至少独立重复两轮。
- 同时记录峰值显存、Megatron step time、tokens/s 和 loss 变化。
- 只有正确且收益大于本轮测量波动的候选才进入分派表；其他形状使用原始 Megatron 实现。
- 项目最终以完整训练吞吐和时间指标验收，算子微基准提速只作为过程证据。

## 5. 计划提供的 Git 可运行内容

后续在 `experiments/megatron_ops/` 提供：

```text
experiments/megatron_ops/
├── README.md                 # BI-V150 运行命令和结果解释
├── probe.py                  # 环境、设备和 Megatron commit 检查
├── capture_workloads.py      # 捕获真实形状和调用信息
├── bench.py                  # 统一正确性、计时与结果保存入口
├── operator_registry.json    # 五个训练算子及未来四个微调算子注册表
├── references.py             # Megatron/PyTorch 正确性参考
├── candidates/               # 手工或编译器生成的候选入口
├── scripts/run_smoke.sh      # 单卡冒烟验证
└── scripts/run_distributed.sh# 双卡 TP/EP 验证
```

运行入口接受 `--megatron-root`，不复制或修改远程机器已有的 Megatron 安装。结果默认写入被 Git 忽略的 `results/`，保存失败候选及诊断，源码和脚本通过 Git 同步。

## 6. 第一批实施顺序

1. 环境探测、commit 检查和现有 GPU smoke test；
2. 真实工作负载捕获与统一结果格式；
3. SwiGLU、Residual Add RMSNorm 前向和反向基准；
4. Dense Attention 单卡基准；
5. Cross Entropy TP=1/TP=2；
6. MoE Grouped GEMM 单卡/双卡；
7. 接入 Halide IR 规范化和 Poly 候选生成；
8. 接回 Dense/MoE 短训练，对比 step time、tokens/s、峰值显存和 loss。

CAKE 的可参考原则是用显式、可检查的调度表示连接候选生成、编译验证和实测反馈；它不能替代本项目的 Halide、Poly 实现，也不能替代 BI-V150 上的前反向及分布式验证。
