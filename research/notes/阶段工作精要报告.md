## 1. 项目要解决什么问题

项目面向大模型训练和微调中的算子优化。算子就是矩阵乘法、归一化等基本计算；目标是让程序自动找到正确且更快的执行方法，并在天数 GPU 和目标训练框架中体现收益。

根据原始项目材料，近期指标包括：2026 年 12 月完成至少 **5 种核心训练算子、4 种微调特殊算子**的编译优化；2027 年 6 月验证训练吞吐提升 15%、时间减少 12%，微调吞吐提升 17%、时间减少 15%。这些是任务目标，尚未达成。[项目依据与范围](项目与CAKE初步调研.md)

三个关键词已明确为：

| 关键词 | 通俗解释 | 拟开展的工作 |
|---|---|---|
| **Halide IR 规范化** | Halide 是描述计算及其执行安排的语言与编译工具；IR 是编译器内部的计算表示；规范化就是统一写法 | 整理循环、索引和冗余表达，保留计算含义，方便后续分析 |
| **Poly 模块优化** | 暂按多面体/循环优化模块理解，用数学方法分析循环如何安排；实际职责待源码确认 | 从分块开始产生候选，检查依赖和资源限制，再逐步考虑重排与融合 |
| **自动化算子优化流程** | 让程序自己完成尝试、检查和比较 | 连接候选生成、编译、正确性检查、计时、反馈与记录 |

拟实现的主流程：**统一计算表示 → Poly 产生候选 → 编译 → 检查结果 → 天数 GPU 计时 → 调整候选 → 接回训练验证。** 这条完整流程尚未接通。

## 3. CAKE 最值得借鉴的核心要点

1. **让智能体选择有意义的执行方案。** 用明确的调度表示描述分块、数据搬运、并行分工等选择，由编译器处理机械细节；对应论文 §2。
2. **先检查，再上设备验证。** 类型、资源和依赖检查能提前排除部分坏方案；真实正确性和性能仍需执行确认，静态检查不是完整正确性证明；对应 §3–4。
3. **把重复失败变成可执行规则。** 保存失败样例，形成检查与回归测试，逐步改进编译环境；对应 §3.2。不能据此认定所有规则更新都已实现无人监督自动合并。
4. **统一表达，保留可检查的含义。** 用规范形式减少无意义的写法差异，为分析和测试提供基础；对应附录 B.1。这是本项目 Halide IR 工作最直接的方法依据。
5. **区分单个输入提速、多输入适配和完整训练收益。** 按输入选择实现称为分派（dispatch），不适用时使用原实现称为回退（fallback）；换硬件仍需重新验证后端与性能；对应 §6、§8。

CAKE 提供设计方法，**没有直接提供本项目的 Halide/Poly 改造方案，也没有证明这些收益可直接迁移到天数**。论文中的内核加速、API 耗时和端到端吞吐使用不同口径，不能混用。[CAKE 原论文](https://arxiv.org/abs/2608.12629v1)；[精读与证据边界](CAKE论文精读与核心要点.md)

ATREX 的补充启发是按真实模型运行记录选择热点，并借鉴搜索、验证和失败恢复的组织方式；不能仅因回退实现算对，就把该次任务计为自动生成成功。[已有调研](项目与CAKE初步调研.md)

## 4. 已编写的代码与本机实验成果

已提供环境探测、CPU 基础计算、扩展 CPU 检查、Triton 向量加法/矩乘候选、结果比较和计时选优代码。报告记录输入、配置、环境与源码校验值，默认生成新 JSON，保护已有记录。GPU 候选仍是手工编写，尚未接入 Halide、Poly 或智能体搜索。[代码及使用说明](../../experiments/basic_validation/README.md)

2026-09-09 在 Windows 11、Python 3.12.14 上实际得到：

| 检查 | 结果 |
|---|---|
| 原有 CPU 基础计算 | 18/18 个配置通过 |
| 扩展向量加法 | 540/540 个配置通过，最大绝对误差 0 |
| 扩展矩阵乘法 | 360/360 个配置通过，最大绝对误差约 2.66×10⁻¹⁵ |
| 错误拦截与选优规则 | 6/6 项通过 |
| 标准库单元测试 | 最初 7 项，扩充后 9/9 项通过 |
| GPU 尝试 | 本机缺少 PyTorch/Triton，记录为 `gpu_unavailable`，未执行 GPU 内核 |

扩展检查覆盖不同尺寸、不能整除的尾部、单行/单列、超大分块、全零、小整数及随机浮点输入。小整数矩乘使用精确整数参考；随机浮点使用 `math.fsum` 累加参考，固定绝对/相对容差为 `1e-12`。900 是配置检查数量，并非 900 个不同算子或完整输入覆盖。

故意注入尾部错值、缺少元素、NaN 和无穷大，都被拒绝；给错误候选附上很快的**虚构耗时**，也不会入选。这验证了筛选规则，未测量性能。

另一个独立数值诊断显示：依次累加 `10^16、1、−10^16` 得到 0，改成 `10^16、−10^16、1` 得到 1；数学结果为 1。前一种结果没有通过数学参考比较，该例不计入上述 900 个配置。它说明后续优化必须约束浮点累加顺序；当前分块实现仍保留 K 方向累加顺序，不能把此例归因于改变分块大小。

**阶段成果是可复用的功能检查程序、边界样例和错误拦截规则。尚无算子提速或训练收益结论。** 完整记录与复现命令见 [CPU 实测报告](CPU基础验证结果.md)。第三方 `cake-ir` 的 Windows 验证另因缺少 pytest 和 Unix `fcntl` 模块未完成，不能与自编 CPU 脚本的通过结果混为一谈。[第三方验证记录](local-validation.md)

## 6. 下一步最直接的工作

1. **先确认天数单卡环境。** 使用实际服务器的 Linux、COREX 和匹配的厂商 PyTorch/Triton，先探测，再跑向量加法，最后尝试矩阵乘法。CPU 用于提前检查流程；项目性能结论必须来自真实天数设备，NVIDIA 上的结果只能作为单独参考。
2. **取得实际模块和训练基线。** 当前仍缺项目 Halide、Poly、九格训练源码及目标设备运行证据。先确定一个模型和真实耗时热点，再选择训练算子。
3. **接通一个算子的三个关键词。** 先验证 IR 整理前后含义一致，再接 Poly 分块候选，最后自动编译、检查、计时和记录。对比原始、规范化、加入 Poly、加入自动搜索四个版本。
4. **扩大可信覆盖后回到训练。** 增加未参与选参数的输入、前后向和梯度检查，记录变慢或回退的情况，最后验证完整训练步骤。规范化可能只改善表达，不保证单独提速；各模块的贡献需要对照实验确认。
