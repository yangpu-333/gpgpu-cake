# 自动化大模型训练算子编译优化：项目理解与 CAKE 初步调研

日期：2026-09-08。定位：启动阶段的技术判断与实施建议，不是性能复现报告。

本报告中的论文、源码和原始附件路径来自调研时的本地目录。远程 clone 后，可按[资料索引](../README.md)下载公开论文及源码；原始项目说明和厂商附件仅在原机保存。

## 1. 项目到底要完成什么

| 节点 | 明确要求 | 当前资料能确认的情况 |
|---|---|---|
| 2026-06 | 至少一种模型的训练/微调瓶颈分析；计算图优化支持至少一种模型 | 文档勾选了使用手工融合算子库支撑计算图指标；目录中未发现相应源代码或分析报告，不能据勾选认定验收完成 |

任务书大图还含通信优化、GPU 资源管理和安全评测等课题任务。应以图中“本课题任务指标”及本目录正文界定当前工作，不能把整个上位课题全部算进算子优化范围。

文档中的技术关键词有三项：自动化优化、Poly 模块优化、Halide IR 规范化。目前没有 AutoFlow、Poly、Halide 或九格实现代码，暂时无法判断其接口和既有完成度。**CAKE 与这些关键词存在方法上的关联，但不是可以直接替换它们的现成模块。**

## 2. CAKE 应该怎样理解

[CAKE 论文](https://arxiv.org/abs/2608.12629)提出编译器与智能体协同演化：智能体编写带类型、显式表达硬件调度的 IR；编译器检查资源、数据流和同步等约束，提供可定位反馈；反复出现的失败进一步推动 IR、检查规则和代价模型更新。IR 表达 warp 分工、缓存及流水线，地址等机械细节由 lowering 推导。论文另将单形状优化与多形状 dispatch 分成两阶段。静态检查不等于全局正确性证明。（正文 §2–4、§6，附录 B–C）

最有辨识度的受控实验是 B200 上固定形状 Flash-KMeans：每组 3 次、每次 8000 万 token 预算，CAKE 最佳加速比的中位数为 1.144×，直接 CUDA/PTX 为 0.928×，均相对同一调优基线。它说明该实验下结构化环境有价值，不能外推为国产 GPU 或端到端训练收益。（论文 §5，Table 2）

对本项目的推论：最值得先实现的是**可复用的硬件契约、可定位诊断和可信评测闭环**。只让模型生成 Triton 代码再反复计时，不能完整体现 CAKE 的研究贡献；一开始重建整个低层编译器，又会显著增加年底交付风险。

### 3.1 第三方 cake-ir：实际读到的代码边界

固定提交：`b0fc98aeff065e464e958c475fa607bdd8e3c686`。下列路径均相对于该源码快照。

| 阅读入口 | 实际能力与限制 | 本项目处理建议 |
|---|---|---|
| `src/cake_ir/ir.py`、`builder.py`、`types.py` | 类型化 IR、构造接口、规范序列化 | 借鉴 workload 和 schedule 数据结构；不要把存储格式规范化等同于 Halide 语义规范化 |
| `targets.py`、`verifier.py` | NVIDIA target 表、资源和操作约束；默认 warp size 32，部分 WMMA 检查直接乘 32 | 新增真实天数 target 及能力检查，逐条审计硬编码 |
| `backends/cuda.py` | pattern 后端要求恰好一个顶层 compute op；单独的 barrier/sync 等 schedule op 虽可验证，但显式拒绝 lowering | 不能据 IR 词汇覆盖声称已有复杂流水线代码生成 |
| 同上 | FP32 SIMT GEMM、FP16 WMMA、配置化 CUTLASS GEMM、FP32 逐元素等有限路径 | 用于理解编译链；不直接承诺 BF16 训练融合内核覆盖 |
| `cost.py` | 简单 FLOPs/访存量与校准 roofline；无校准时不返回延迟，当前要求一个顶层计算 | 可做筛选基线；复杂流水线、占用率、同步和融合代价需要另建模型 |
| `harness.py` | 接收外部 oracle/benchmark；正确性通过才计时，保存证据 | 借鉴接口，但它本身不是完整自动搜索智能体 |
| `dispatcher.py`、`external.py`、`frozen.py` | guards、fallback、外部 provider 或固定源码接入 | 区分“生成原生代码”和“调用已有算子”，分别统计 |
| `cache.py`、`compiler.py` | NVCC 编译、缓存和加载路径；导入 Unix `fcntl` | 需要 Linux 环境与天数工具链适配，不是替换一个命令即可 |

源码 README 同样将原生 WGMMA、tcgen05、TMA descriptor lowering 和自动调度搜索列为待完成能力。这与后端代码中的显式拒绝一致。仓库的 FlashInfer 复用审计是 2026-08-17 的快照，其“19 个 PR”等统计不能作为 9 月现状。

## 4. 天数适配的现实基础

依据用户提供的《天数智芯加速卡软件栈文档合集 V4.3》；这是版本资料，不代表服务器当前安装状态。本次针对编译、迁移、Triton 与工具相关章节检索阅读，没有通读全部 1277 页。

| 文档证据 | 适配含义 |
|---|---|
| §28.6.3，PDF p376；§30，p389–391：warp size 64、CUDA API 兼容但需重新编译 | 审计 warp/lane/归约/同步假设，不能复用 NVIDIA 二进制或默认 32-lane 调度 |
| §39，p487–488：适配 Triton 3.1.0，`third_party/iluvatar`，提到 SME 和平台 mma | 优先验证已有天数 Triton 路径，再决定是否开发专门低层后端 |
| 软件栈概览与工具说明：ixKN、ixSYS、ixPROF、ixPTI、ixSAN | 分别对接热点/trace、内核计时与合法性检查；实际命令和覆盖需服务器确认 |

建议按能力处理 TMA/TMEM/tcgen05/PDL 等 NVIDIA 特性：在当前提供资料中没有找到足以证明等价支持的证据，应先标为“未验证”，为每项设计 capability probe，不能自动当作受支持，也不能断言所有天数型号永久不支持。

新增天数后端至少涉及 target、编译参数、runtime/stream、性能采样和指令合法性五个接口；如果使用更低层 IR，还需重新建立矩阵 tile、内存搬运与同步语义。

## 5. 三条路线怎样组合

以下是工程建议，而非文献已经验证的结论。

| 路线 | 在项目中的建议角色 | 主要缺口 |
|---|---|---|
| AutoFlow | 图/子图分析、优化和 Triton 生成的上层入口 | 原图明确从 `forward()` 输入走向 inference assembly；需补训练图、反向及状态更新。文档无具体论文/仓库链接，暂不匹配同名项目 |
| CAKE 思路 | 中层 schedule 契约、硬件约束、诊断和规则积累 | 官方实现未取得；第三方覆盖窄；天数后端待建 |
| ATREX | 借鉴搜索编排、profiling、验证、失败恢复和经验库 | 当前公开支持列表未列天数，不能认为已有可用适配 |

[ATREX 论文](https://arxiv.org/abs/2607.14541)以真实推理 trace 的算子和形状权重组织评测，强调正确性与真实目标 DSL 实现应分开衡量。对本项目最直接的启发是：先按九格训练耗时确定优化对象，并记录优化路径命中率，不能靠回退通过测试后就计入“自动生成成功”。

本次下载的 [ATREX 源码](https://github.com/alibaba/atrex-kernel-agent)固定在 `d643fb5bc004ed021d1a60aa99bf9513204d3025`，阅读了 README 和 `orchestrator/optimize.py` 入口，并查看模块组织。后续建议重点读 `hardware.py`、`workspace_runtime.py`、`optimization_policy.py`，先理解设备适配、执行环境和验收控制。没有在本机启动优化 campaign。

建议系统链路：

```text
九格训练/微调 trace + 数学与梯度参考
    → 固定 workload 契约：shape / dtype / stride / 梯度 / 精度容差
    → 图或子图规范化与融合候选（AutoFlow / Poly / Halide 接口待确认）
    → 调度候选 + 天数硬件约束 + 编译器诊断
    → 天数 Triton / 必要时 COREX C++ 后端
    → 正确性、梯度、内存检查 → 实测与 profiling
    → 多形状路由与回退 → 九格端到端回归
反复出现的失败 → 经独立回归测试的新规则或后端能力
```

Poly 与 Halide 的第一步应是建立接口清单：输入/输出 IR、规范化 pass、依赖分析、可融合范围、动态 shape 和别名语义。建议保留现有表示，先做一个小子图的桥接；不要为了 CAKE 名称把全栈统一改写。

## 6. 建议的首批工作和算子选择

**优先建立基线，再决定 5+4 的最终名单。** 下表只是候选池，不是已确认的验收计数；前后向算一个还是两个、训练与微调能否重复计数，应从任务书口径明确。

| 候选 | 为什么可能有价值 | 选择条件 |
|---|---|---|
| RMSNorm/LayerNorm 前后向 | 规约、逐元素融合，适合验证完整训练闭环 | 目标模型真实热点 |
| SwiGLU/MLP activation 前后向 | 融合减少中间写回，接近近期 CAKE 训练产出 | 先用既定 BF16/FP16 语义，不先绑定 MXFP8 |
| RoPE 前后向 | 适合 shape/stride/尾部覆盖，开发复杂度较低 | 需避免优化已有足够快且占比很低的实现 |
| attention/softmax 前后向 | 潜在耗时高，但同步、精度和反向复杂 | 简单闭环完成后再进入 |
| GEMM epilogue / grouped GEMM | 可能适用于投影、融合或 MoE | grouped GEMM 以目标模型有 MoE 热点为前提 |
| LoRA 低秩投影、低秩梯度、梯度累积、adapter 参数更新 | 可作为微调特殊算子候选池 | 先确认微调方法确实使用 LoRA/adapter，并确认 4 种计数规则 |

### 首轮 2–4 周建议安排

1. **取得条件并冻结基线。** 九格训练代码、一个目标模型、天数型号及容器版本；记录训练/微调方法、batch、序列长度、并行策略、精度和基线实现版本。保存一轮完整 step 的 trace 与算子形状统计。
2. **选一个闭环样例。** 在热点允许的前提下从 RMSNorm 或 SwiGLU 前后向开始，先实现天数 Triton baseline 和外部参考验证，再接搜索。结果包含实际调用路径，fallback 独立统计。
3. **接入最小反馈。** 第一阶段只优化 tile、向量化、warp 数和融合边界；记录非法配置类别、编译失败、梯度误差、显存与时间。用微基准校准带宽/矩阵性能，不照搬 B200 参数。
4. **做首次方法对照。** 同一模型、形状、参考实现、预算，对比无结构化反馈与有反馈；比较正确率、有效候选数、编译/GPU 时间、最终性能和 token 成本。第二轮才研究新规则是否跨算子有效。

到 2026-12 的建议节奏：9 月完成基线与一个闭环；10 月完成核心训练候选及自动化记录；11 月补微调特殊算子、梯度与形状覆盖；12 月完成集成、回归与交付文档。此安排以硬件和框架及时到位为前提。

## 7. 如何保证实验能支撑验收

端到端吞吐和时间要基于相同有效 tokens、硬件数量和训练工作量。固定工作量下，吞吐提升 15% 对应时间约下降 13.04%；提升 17% 对应时间约下降 14.53%，**尚未达到微调时间下降 15%**。满足后者需要吞吐约提升 17.65%。若指标按不同定义统计，应分别验收。

用 Amdahl 粗筛优化价值：若可优化部分占 step 时间 p，局部加速 s，则总加速近似 `1 / ((1-p) + p/s)`。例如 p=30%、s=2，理想总加速约 1.176；若 p=10%，即使无限加速也只有 1.111。该估算忽略通信重叠和调度变化，最终以实测为准。

建议保存以下证据：

- 单算子：固定形状与留出形状、stride、尾部、数值分布、梯度检查、预热和计时范围、重复运行波动。
- 子图与训练：前向+反向+optimizer step，显存和保存张量，图断裂、通信占比、loss 轨迹；短程一致性用于开发，更长训练用于验收。
- 自动化：总候选、实际编译数、正确候选、真实新实现占比、回退命中率、搜索耗时和 token 成本。
- 可追溯性：代码提交、生成源码摘要、设备及软件版本、随机种子、外部参考、未通过测试及完整 benchmark JSON。

不要把相对 PyTorch eager 的收益全部算成编译研究贡献；应同时对比项目原始配置、现有厂商/框架优化路径以及所提自动化方案。任何优化器都不能修改用来判定成功的输入、容差或参考结果。

## 8. 当前结论与待补输入

**建议采用“现有天数 Triton 后端 + CAKE 式结构化反馈 + 真实训练 trace 驱动”的起步方案。** 先得到可集成的训练闭环，再根据热点证明开发专用 IR/后端的必要性。手工高性能实现仍可充当基线和参考，不宜成为唯一自动化交付。

进入复现阶段前缺少四项决定性输入：九格训练仓库、实际 GPU/COREX 环境、目标模型及微调方法、5+4 算子计数与端到端基线口径。AutoFlow 的准确源码来源及 Poly/Halide 现有模块也应同时收集。

本次完成的是资料获取、论文和关键代码阅读、官方状态核验及适配判断。Windows 本机导入遇到 `fcntl`，pytest 也未安装；未通过完整 CPU 测试，未运行 NVIDIA/天数 GPU 正确性或性能实验。详见 [本机验证记录](local-validation.md)。
